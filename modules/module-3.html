Object-Oriented Architecture

Everything so far has lived inside one _MenuScreenState class, mixing "what the score is" together with "how the score looks on screen." That's fine for a tiny demo, but our game is about to grow a Player, obstacles, a scrolling background, and gravity. Cram all of that into one widget and it turns into a mess nobody can read — including future you. This module is about splitting things up properly, before that happens.

1. Classes and Objects: The Cookie Cutter

You've already been using classes without thinking about it — MenuScreen is a class, and so is GameMenuApp. A class is a blueprint that describes what something looks like and what it can do. An object (or "instance") is an actual thing built from that blueprint.

Analogy: a class is a cookie cutter. It defines the shape — a star, say — but it isn't a cookie itself, and it doesn't get eaten. Every time you press it into the dough, you get a new cookie (an object) with that shape. You can stamp out as many cookies as you like from one cutter, and each one is separate — frost one, and the others don't change.

2. Encapsulation: The Vending Machine

Right now, our score is just a raw number sitting inside a widget, and anything in that widget can change it directly: _score++. That's risky once your game gets bigger — what if some other part of the code accidentally sets the score to a negative number, or forgets to check if the player still has lives left?

Analogy: think of a vending machine. You don't open the back panel and grab a can yourself — you press a button, and the machine handles dispensing the can, checking your money, and updating its own stock count internally. You only interact with it through its buttons (its public methods), never by reaching inside. That's encapsulation: keeping an object's data private, and only allowing controlled changes through methods you've written on purpose.

3. Separating Logic from UI: Script vs. Actor

This is the big idea for this module. Instead of storing game data directly inside a widget's state, we'll create a plain Dart class that holds the data and the rules for changing it — with no Flutter, no widgets, nothing about pixels or colors at all. The widget's only job becomes: show whatever that class currently says, and call its methods when the player does something.

Analogy: think of a play. The script decides what happens — when a character scores a point, when they lose a life, what the rules of the story are. The actor just performs whatever the script currently says, out loud, for the audience to see. You could swap in a completely different actor (a different UI — maybe a bar chart instead of text) and the script wouldn't need to change at all. That separation is exactly why Module 4's Player, Obstacle, and Background classes will work independently of however we choose to draw them.

Example 1: Extracting a GameSession Class

Let's pull the score and lives logic out of _MenuScreenState and into its own class, GameSession. It keeps _score and _lives private, and only exposes them through getters (read-only access) and methods like addPoint() and loseLife() — the vending machine buttons.

Replaces the entire file 
import 'package:flutter/material.dart';

void main() {
  runApp(const GameMenuApp());
}

/// Holds the game's data and rules — no widgets, no UI, just logic.
class GameSession {
  int _score = 0;
  int _lives = 3;

  int get score => _score;
  int get lives => _lives;
  bool get isGameOver => _lives <= 0;

  void addPoint() {
    _score++;
  }

  void loseLife() {
    if (_lives > 0) {
      _lives--;
    }
  }
}

class GameMenuApp extends StatelessWidget {
  const GameMenuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Game Menu',
      theme: ThemeData(useMaterial3: true, primarySwatch: Colors.indigo),
      home: const MenuScreen(),
    );
  }
}

class MenuScreen extends StatefulWidget {
  const MenuScreen({super.key});

  @override
  State createState() => _MenuScreenState();
}

class _MenuScreenState extends State {
  final GameSession _session = GameSession();

  void _addPoint() {
    setState(() {
      _session.addPoint();
    });
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Sky Runner')),
      body: Padding(
        padding: const EdgeInsets.all(24.0),
        child: Column(
          mainAxisAlignment: MainAxisAlignment.center,
          crossAxisAlignment: CrossAxisAlignment.center,
          children: [
            const Text(
              'Welcome, Player!',
              style: TextStyle(fontSize: 28, fontWeight: FontWeight.bold),
            ),
            const SizedBox(height: 24),
            Container(
              padding: const EdgeInsets.symmetric(horizontal: 20, vertical: 12),
              decoration: BoxDecoration(
                color: Colors.indigo.shade50,
                borderRadius: BorderRadius.circular(12),
              ),
              child: Row(
                mainAxisSize: MainAxisSize.min,
                children: [
                  const Icon(Icons.favorite, color: Colors.red),
                  const SizedBox(width: 8),
                  Text('Lives: ${_session.lives}', style: const TextStyle(fontSize: 18)),
                  const SizedBox(width: 24),
                  const Icon(Icons.star, color: Colors.amber),
                  const SizedBox(width: 8),
                  Text('Score: ${_session.score}', style: const TextStyle(fontSize: 18)),
                ],
              ),
            ),
            const SizedBox(height: 32),
            ElevatedButton(
              onPressed: _addPoint,
              child: const Text('Tap to score a point!'),
            ),
          ],
        ),
      ),
    );
  }
}

Notice the widget got simpler, not more complicated. _MenuScreenState no longer knows or cares how scoring works — it just calls _session.addPoint() and redraws. All the actual game rules live in GameSession, completely separate from anything Flutter-related. You could copy that class into a totally different app and it would still work.

4. Multi-Page Navigation: A Stack of Index Cards

Right now everything happens on one screen. Real apps — and our game — need more than one: a menu, a game screen, maybe a game-over screen later. Flutter handles this with something called the Navigator.

Analogy: think of your screens as a stack of index cards on a desk. You only ever see the card on top. Navigator.push() lays a new card down on top of the stack — that's you moving to a new screen. Navigator.pop() lifts the top card away, revealing whatever card was underneath — that's the "back" behavior you get for free, including that back arrow that shows up automatically in the app bar.

To push a new screen, you wrap the widget you want to show in a MaterialPageRoute, which just tells Flutter how to animate the transition: 

Navigator.push(
  context,
  MaterialPageRoute(builder: (context) => const GameScreen()),
);

Example 2: Adding a Game Screen

Let's add a "Play" button to the menu that pushes a new GameScreen. We'll hand it our existing GameSession object — proof that separating logic from UI pays off, since the same session object can now be shared between two completely different screens.

              child: Row(
                mainAxisSize: MainAxisSize.min,
                children: [
                  const Icon(Icons.favorite, color: Colors.red),
                  const SizedBox(width: 8),
                  Text('Lives: ${_session.lives}', style: const TextStyle(fontSize: 18)),
                  const SizedBox(width: 24),
                  const Icon(Icons.star, color: Colors.amber),
                  const SizedBox(width: 8),
                  Text('Score: ${_session.score}', style: const TextStyle(fontSize: 18)),
                ],
              ),
            ),
            const SizedBox(height: 32),
            ElevatedButton(
              onPressed: _addPoint,
              child: const Text('Tap to score a point!'),
            ),
            const SizedBox(height: 16),
            OutlinedButton(
              onPressed: _openGameScreen,
              child: const Text('Play'),
            ),
          ],
        ),
      ),
    );
  }
}

class GameScreen extends StatelessWidget {
  final GameSession session;

  const GameScreen({super.key, required this.session});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Game')),
      body: Center(
        child: Column(
          mainAxisAlignment: MainAxisAlignment.center,
          children: [
            Text(
              'Score so far: ${session.score}',
              style: const TextStyle(fontSize: 24),
            ),
            const SizedBox(height: 16),
            const Text('The actual game world arrives in Module 4!'),
          ],
        ),
      ),
    );
  }
}

The key additions are: a new GameScreen widget that takes a GameSession in its constructor and displays its current score; a "Play" ElevatedButton on MenuScreen that calls Navigator.push(), passing the existing _session along; and because GameScreen is wrapped by MaterialPageRoute and pushed onto a Scaffold, Flutter automatically gives it a back arrow in its app bar — no extra code needed.

Recap

  • Understood classes vs. objects (the cookie-cutter analogy)
  • Used encapsulation to keep GameSession's data private, exposed only through getters and methods
  • Separated game logic (GameSession) from UI (MenuScreen) — the script-and-actor split
  • Added a second screen and navigated between them with Navigator.push()
  • Passed an object between screens instead of using globals

With logic and UI properly separated, we're ready for the fun part. In Module 4: Game Entities, we'll build real OOP classes for the Player, obstacles, and a scrolling background — each one following the exact same pattern as GameSession: a plain Dart class holding the data and rules, drawn to the screen by a widget that just displays whatever state it's given.
